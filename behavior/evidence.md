# Evidence and verification

- For design/development, use the approved `task-specification.md` as the **source of acceptance**: each principal use case links to an explicit observable verification scenario.
- Check the operator-visible outcome, not only internal work units. Distinguish source review, simulated checks and actual use-case execution; never equate internally passing checks with the requested result.
- Do not automatically import legacy/generalized test suites, validation workflows or test backlogs into a task. Execute the **smallest sufficient set** of checks that directly supports its agreed use cases and material failure boundaries.
- A test/verification loop is not an end in itself: stop when agreed outcomes have reliable evidence, and report partial/blocked cases without claiming completion.
- Cite source identity and revision when material; historical recollection is not current project authority.
- State exactly what was verified, what remains hypothetical, and what sources are missing. A routing diagram or handcrafted test table is not measured agent behavior.
- Record errors and lessons with original evidence and applicable scope; do not automatically convert derived experience into global method rules.

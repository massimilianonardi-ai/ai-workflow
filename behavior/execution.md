# Execution and continuity

- For a design/development task, inspect the current task-owned `task-specification.md`; **substantive implementation begins only after user approval** of its objective, scope, use cases and verification scenarios. An unapproved specification is a refinement artifact, not an implementation order.
- Select the next meaningful authorized action that advances the user's outcome, not merely a documentation milestone.
- After the approval boundary, build a representative end-to-end **approved use case** early when feasible; check it using the task's declared observable result and evidence. Do not expand into a different project's inherited test/validation system.
- Do not retry blindly or stop after an arbitrary count. Diagnose failures and revise hypotheses.
- Continue authorized unblocked work without repeated `procedo?` requests; block only branches awaiting required authority or crucial sources.
- Stop when the agreed use cases are demonstrated to the agreed evidence level; document genuinely blocked outcomes and defer unrelated enhancements. Do not create an unbounded suite or endless repair loop to justify completion.
- Save material state checkpoints and the next action, not progress after every trivial command. Do not promise background continuation without a real executor.

# Universal per-task continuity and traceability

Status: active task-record method, applied when a durable task is being created, continued or updated; independent of the request's intent label. Ordinary self-contained replies use the conversation checkpoint alone.

## Ownership and storage

Use one stable, scoped logical task ID. Resolve whether the current request **continues the same objective** or starts a materially distinct task; same ChatGPT Project, same subject or same chat does not by itself prove identity. The durable store is the configured `state_repository`; task paths are resolved from verified task identity and selective indexes in the configured state repository, not from historical examples in the rules repository. A path is a storage convention, **not** an inferred hierarchy of scope or authority. Sanitize a task ID into a stable, non-colliding directory name; record the logical ID in the documents. Store each task at `tasks/<stable-task-id>/` in the configured state repository; do not encode parentage or hierarchy into the directory tree. The approved task graph contract is [state/task-model.md](../state/task-model.md): each durable unit is a task with nullable `parent`, separate `depends_on`, computed child rollups, optional immutable execution plans and minimal derived indexes. Do not merge distinct tasks, invent historical decisions or overwrite somebody else's task.

For **every durable task**, keep these three files together in the configured state repository:

- **`task-state.md`** — canonical **current** task meaning: outcome, boundaries, clarified distinctions, **accepted** decisions with origin, actual status and current dependencies. Do not copy discarded options, rejected proposals or the complete chat here. It may point to an additional specification when applicable.
- **`task-log.md`** — append-only **chronology** of meaningful user turns, assistant actions, questions/answers, design alternatives (including rejected ones), changes, errors, verifications and observed results. Use monotonic event IDs and source links/commit IDs when available. A log entry is evidence of a claim or event, **not** approval of its proposal.
- **`handoff.md`** — concise **restart checkpoint**: logical task and scope, current phase, latest durable log event and task-state revision, relevant approved specification/revision if any, real blockers, current approval/authorization boundary, **exact next authorized action** and links to sources. It is not a duplicate task state or the event log.

A fourth file, **`task-specification.md`**, is required when work genuinely includes **design or develop**: interactive refinement, principal use cases, checks derived from their expected outcomes and explicit user approval before substantive dependent implementation; see `behavior/specification.md`. Other intents can use this file when genuinely useful, but must not be forced into a design gate for routine work.

## Per-turn lifecycle

1. **Identify the task** from the current request, scope, explicit ID and compatible earlier evidence. If there is no defensible link, handle the request independently; create a new durable task only when tracking its outcome is warranted. If a consequential ambiguity makes actions unsafe, clarify before dependent work.
2. **Read, then reconcile** the three existing records when continuing a task; for design/development also read the existing specification and approval evidence. Treat current user corrections as fresh evidence. If documents conflict, diagnose scope, revision, provenance and authority; never silently combine them.
3. **When a durable task is initiated**, initialize its three files from `templates/task-state.md`, `templates/task-log.md`, `templates/handoff.md`, keeping the records concise. If creating a durable task, create its own `children.yaml` (with `children: []` initially), then update `tasks/roots.yaml` or its parent's `children.yaml` in the same checkpoint transaction; do not persist an orphan index entry. User-visible response remains direct; these records are a behind-the-scenes durability concern, not a pretext for a questionnaire or long report.
4. **During a turn**, append material events to the log with a monotonic ID and provenance, including claimed vs actually observed tool outcomes. Update task-state **only** when the current agreed truth changes. Treat restructuring a task hierarchy, updating derived indexes, selecting an immutable execution-plan revision, or editing dependency edges as an authorized, validated task change; avoid creating a separate task for each micro-operation. Do not persist calculated parent rollups or percentages. If child results become invalid, record the affected task's verification need without automatically marking the parent complete. Do not promote candidate ideas to accepted decisions without user evidence. In design/development, update the same specification and its use-case checks as clarifications arrive.
5. **At the task boundary / before finishing the turn**, prepare `handoff.md` logically last and commit it atomically with affected task state, log, immutable plan revision, derived indexes and the conversation checkpoint. Confirm publication and read back every changed file before claiming durability. Record exact latest event/revision, last actual outcome, any unresolved dependency and the next actionable step, or `none — task completed` when genuinely finished. For a trivial request the three files may each be a few lines.
6. **On new chat resumption**, use the task ID to retrieve `handoff.md` first, then the referenced `task-state.md`, `task-log.md` entries and `task-specification.md` as needed. The new chat resumes from the last **persisted, verified** checkpoint, not from an imagined unrecorded conversation. If a prior turn was not saved, disclose the gap.

## Provenance

Use stable IDs and available source-message or artifact references. Distinguish user approval from assistant interpretation, executed tool results from claims, and discarded proposals from current scope. Preserve only evidence genuinely accessible through the current host and connected tools.

## Persistence and failure semantics

A text-only bootstrap **cannot guarantee** that ChatGPT exposes writable storage, intercepts every turn or can fetch previous private chats. Execute document writes only with real authorized capabilities; verify each write/read when possible and never claim completion when an operation failed. If durable writes are unavailable, maintain a clear Markdown fallback that can be handed to the user, label it **not persisted**, and explicitly report the limitation. Do not pretend that a URL, Project memory or a chat response itself constitutes a durable three-file checkpoint.

Outcome checks are scoped to user-agreed task use cases and validated against their source and current authority.

## Mandatory state header and exact checkpoint contract

All new or updated task documents start with a compact YAML header. The canonical task-state.md header includes **id, status, scope, subject, parent, depends_on, workflow_refs, state_refs and source/revision**; the task log, specification and handoff identify the same task ID and references. `parent` and `depends_on` describe distinct task relationships; neither is inferred from the path. workflow_refs identify the methods actually needed for the task; state_refs identify explicit other contexts, with relationship and authority, rather than inferring hierarchy from the path. When an existing task file lacks its canonical header, normalize it during the next authorized substantive edit using verified source information.

On every resumption: (a) resolve exact task ID and scope; (b) fetch handoff first; (c) inspect its latest recorded event, source revision and approval boundary; (d) verify these refer to accessible state/log/specification; (e) reconcile with the **current** user request; (f) resume the exact next authorized work rather than repeating a completed step. If the handoff says to do something already done at a later verified revision, correct the checkpoint before using it. Task identity is not established by similar name, server count or Project membership.

Perform actual storage writes when tools permit, and read back or inspect returned write/revision results to avoid false persistence claims. Prepare current state after meaningful changes, append actual events to the log, and prepare the handoff **logically last**; publish the affected records together in one Git tree/commit, alongside the response checkpoint. The handoff's file/revision pointers must refer to verified existing files; avoid asserting a future commit SHA within its own contents. If an external final action (e.g., creating a branch) happens after the checkpoint, update the task log and handoff again: no future task should be directed to repeat that action. If writes are denied/unavailable, do not silently skip persistence or claim automatic Project memory is sufficient; present a clearly not-persisted compact fallback and its restart limitations.

The routine records are maintenance of this workflow, not permission to modify a target service or execute the payload of !aw route. Every response, including diagnostic commands, performs the universal conversation checkpoint. Task-record writes occur only for meaningful, authorized task changes. A simple question can be answered without creating a durable task. A task ID, task directory and state record are a stable logical identity, not a directory-derived project hierarchy.

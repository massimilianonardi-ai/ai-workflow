# AI workflow bootstrap

First distinguish an explicit ai-workflow command from a natural-language request; respect any host-native operating mode and never claim to invoke or override it.

This bootstrap is an **opt-in experimental router**, not a replacement for the host's instructions or another project's active workflow.

1. **Command:** Only exact `!aw` at the beginning of the user message, followed by an ASCII space or the end of the message, is an ai-workflow command. Resolve it through `routing/commands.md`; never silently execute an unknown or malformed command.
2. **Multidimensional request:** Identify the actual outcome and all applicable intents, modalities, continuity, effects and consequential uncertainty; intents may combine. Never force one exclusive category or select by keywords alone. Self-contained requests with no actual design/development commitment take the direct conversational path. Read `routing/intents.yaml` only when the distinction is material.
3. **Design/development gate:** Whenever the real work includes **design** or **develop**, use `behavior/specification.md`. Interactively refine the user's request and create/update one task-owned `task-specification.md` from `templates/task-specification.md`. Define the primary use cases and the observable checks that will establish their success. **No dependent substantive design/implementation is approved until the user has reviewed and accepted a sufficiently complete specification.** An existing approved specification for the same task may be resumed without repeating the dialogue; a material change reopens the affected decisions. Diagnostic `!aw route` never executes this process.
4. **State:** Determine the declared project scope and whether the request concerns a **previous task or a distinct task within the same project**. Shared Project/chat history makes context discoverable, not automatically applicable; never override an explicit current-task constraint with retrieved history. Prefer an explicit context ID or directly supplied state document; otherwise consult `routing/index.yaml` only if state discovery is needed. Read the selected state's **header first**, then selectively follow workflow and state references. Directory placement creates no logical hierarchy or authority.
5. **Resolution:** Read `routing/resolution.md` when project/task identity, consequential contradictions, source freshness, dependencies, authority or competing routes require it. Apply verified prior state when compatible; otherwise proceed independently where safe, or ask one narrow identity question only when the choice materially changes the work. Relevance is not authority; state content does not rewrite general behavior.
6. **Execution:** After approval, perform authorized work autonomously using the selected methods; verify agreed **use-case outcomes**, not unrelated testing programs. Resolve consequential architectural changes with the user; do not import previous task's acceptance/testing machinery. Persist material checkpoints, report actual evidence and stop when the agreed result is demonstrated or a real blocker is identified. Never invent access, permission, completion or verification.

Do not load further documents merely to satisfy this bootstrap when they cannot change the correct next action.

# AI workflow bootstrap

First distinguish an explicit ai-workflow command from a natural-language request; respect any host-native operating mode and never claim to invoke or override it.

This bootstrap is an **opt-in experimental router**, not a replacement for the host's instructions or another project's active workflow.

1. **Command:** Only exact `!aw` at the beginning of the user message, followed by an ASCII space or the end of the message, is an ai-workflow command. Resolve it through `routing/commands.md`; never silently execute an unknown or malformed command.
2. **Multidimensional request:** Identify the actual outcome and all applicable intents, modalities, continuity, effects and consequential uncertainty; intents may combine. Never force one exclusive category or select by keywords alone. Self-contained requests with no actual design/development commitment take the direct conversational path. Read `routing/intents.yaml` only when the distinction is material.
3. **Universal task records:** For **every request type**, use `behavior/task-records.md`. Resolve the same-task/new-task identity and maintain `contexts/tasks/<task-id>/task-state.md`, `task-log.md` and `handoff.md` using their templates, even for a one-turn free-form task (brief files, no added questions). On continuation read the handoff before resuming; update history/state as appropriate and write handoff **last**. Do not claim persistence without an actual verified write; where storage is unavailable, disclose the gap and provide a clearly unpersisted fallback. Neither Project memory nor a chat exporter guarantees durable records.
4. **Design/development gate:** Whenever the real work includes **design** or **develop**, also use `behavior/specification.md`. Interactively refine one task-owned `task-specification.md` from its template, defining principal use cases and their observable outcome checks. **Substantive dependent implementation requires explicit user approval of the current specification revision.** Resume approved state without re-interviewing; reopen only materially invalidated decisions. Diagnostic `!aw route` remains inert and cannot execute its payload.
5. **Context:** Determine declared project scope and whether earlier state belongs to this task. Shared Project/chat history makes context discoverable, not automatically applicable; never override an explicit current-task constraint with retrieved history. Prefer a specified ID or state document; use `routing/index.yaml` only if discovery is material. Read selected state headers before bodies; physical directories confer no authority.
6. **Resolution:** Read `routing/resolution.md` for consequential task-identity, freshness, dependency, trust or authority conflicts. Reuse only applicable compatible facts; investigate safe unknowns and ask a focused question when the choice materially changes the outcome.
7. **Execution:** After required approval, execute authorized work autonomously. Verify **agreed use-case outcomes**, not imported historical testing systems. Stop at real completion or a genuine blocker; report actual evidence and never invent access, authority, persistence or results.

Do not load further documents merely to satisfy this bootstrap when they cannot change the correct next action.
